# Artifact provenance across low- and high-privilege CI workflows

## Source-grounded mechanism

A repository uses a low-privilege workflow to build submitted code and upload an artifact. Completion of that workflow can trigger a separate `workflow_run` consumer. The consumer may possess repository write permissions or deployment credentials even when the producer did not. Downloading an artifact from a completed run does not by itself establish that the artifact's source code was trusted. The artifact can contain files controlled by the author of a fork pull request. This experiment studies the authorization to use an artifact in a privileged operation, not the semantics of arbitrary scripts.

## Explicit experimental scope and setup

There is one protected repository and a distinct attacker-controlled fork. A maintainer can create trusted commits in the protected repository. An attacker can submit arbitrary fork commits and control the complete artifact body produced from those commits. The attacker cannot create a trusted protected-repository commit, modify the consumer workflow, acquire its deployment credential, or forge the CI platform's metadata. A trusted origin means the protected repository together with a designated protected branch; a branch-name string supplied inside an artifact is not origin evidence.

The honest CI platform allocates a fresh run ID to each build. It records the source repository, source branch, exact commit, workflow identity, completion status, and the artifact produced by that run. The artifact store creates a distinct artifact identity and records the run ID, artifact name, and body. These records are immutable once the run completes. An attacker can upload artifacts only as the producer of their own fork runs, but may reuse the ordinary artifact name `package`. At least an honest run and an attacker-controlled run can coexist. A completion notification and an artifact lookup response are authenticated platform statements, not unauthenticated caller assertions. An attacker may schedule completion and consumer execution but cannot rewrite those statements. Within the modeled scope, honest protected-branch runs succeed and fork runs can also succeed.

Compare three isolated consumer configurations. Each consumer is triggered by a successful completion notification for the designated build workflow. In `name_only`, it selects an artifact named `package` without tying it to the triggering run; any stored artifact with that name is eligible. In `run_bound`, it selects `package` only from the exact triggering run, but accepts completions from either repository. In `trusted_origin`, it additionally checks authenticated platform metadata that the triggering run used the protected repository and designated protected branch. It then selects `package` from that exact run. The selected body and artifact identity must come from the same immutable store record; no later unbound re-download is allowed. Failed checks prevent privileged use.

After selection, the consumer uses its protected deployment credential to submit the selected artifact for a privileged operation. The deployment service authenticates the consumer and records the configuration, triggering run, selected artifact, producing run, source repository, source branch, exact commit, and body. Being selected does not relabel an artifact as maintainer-produced. Producer metadata and body remain connected through the platform's stored record. The deployment credential is never handed to the producer.

## Security questions

For each configuration, determine whether every privilegedly used artifact came from a trusted protected-branch build, or whether an artifact produced by an attacker-controlled fork can be used. Separately ask whether the selected artifact always belongs to the triggering run, distinguishing accurate run provenance from trusted source authorization. Establish a legitimate protected-branch build-to-deployment execution for every configuration. Scope excludes parser vulnerabilities, path traversal, cache poisoning, compromised CI infrastructure, and claims that all protected-branch code is semantically harmless.
